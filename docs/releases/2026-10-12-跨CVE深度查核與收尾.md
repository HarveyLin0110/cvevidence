## 結論與範圍

第二項目標「任意 CVE 都能給出確切分析與合適結果」**尚未完成驗收**。本輪確實取得超過版本比對的原碼、入口與正常運作分析，也修正實測發現的問題。未修補案例曾因預算耗盡無法收尾；修正互相矛盾的預算指示後，從同一前次紀錄接續完成，但仍非一次從頭成功或跨 CVE 穩定性證明。

## 本輪修改

1. 完成的調查已有必要條件排除線索時，先顯示需要覆核的排除條件，保留其他缺口，不把缺口數量當成繼續大量補件的理由。矛盾仍優先；預算、逾時或失敗仍顯示未完成。增加明確下一步與優先覆核條件。
2. `READ_BATCH` 一次讀 2–3 個來源的相同行範圍，保留每份獨立引文。每檔最多 200 行／24000 UTF-8 bytes，合計 48000 bytes；其中一份失敗，整批不給成功閱讀資格。補件門檻、接續與品質量測共用成功閱讀定義，SEARCH 仍不能冒充已閱讀。
3. 錯誤產品摘錄回報具體條件、X-ID 及同段原文提示，不自動改字接受。收據原文中的外部下載 hash 可以逐字引用，仍須通過原文核對；自由敘述中捏造的 hash 仍拒絕。這不會認證收據或建置者。
4. 依實際回報用量提供剩餘呼叫估算，並新增 `REPORT` 讓模型同一次提交逐項 REVIEW 與三層摘要。保留既有條件、引用、最小補件檢查；不符合條件時不替換最後接受的計畫。模型可繼續使用原流程，估算和提示不是完成保證。
5. 最後回查失敗紀錄發現預算提示仍要求 REVIEW、reserve 欄位未列 REPORT；估計只剩一次時改為 `REPORT_NOW`，剩兩次的覆核亦可直接 REPORT。真正缺件仍受 REVIEW／ASK_USER 檢查，不把未完成改成已支持。

上述變更不擴充正式 verdict 規則，不把 AI 觀察升級成已驗事實。真實 OpenAI API 已連通；Codex CLI 本輪只有共用介面的合成測試，沒有 LIVE 驗收。

## 實際 CVE 與材料

選用現有三個正式 profile 之外的 **CVE-2018-25032**。公開 zlib v1.2.11／v1.2.12 原碼加上本輪新寫的 TEST_ONLY 程式，真正編譯成 ELF，保存 object、link map、編譯命令與退出碼、原碼／成品 hash、普通輸入與輸出。未複製舊 Demo，未送公司 Turnkey 樣本，未執行漏洞輸入。

| 案例 | 真正差異 | 應觀察的範圍 |
|---|---|---|
| alpha | 1.2.11 舊實作，程式只壓縮固定 42-byte 字串 | 舊函式存在，但這個固定輸入入口有排除線索；不可因此說整個 1.2.11 安全。 |
| beta | 1.2.12 修補實作，相同固定輸入入口 | 必須讀到 `sym_buf` 等修補內容，不能只依版本號排除。 |
| gamma | 1.2.11 舊實作，`fread(stdin)` 接受最多 65536 bytes | 具體指出外部輸入到 deflate 的路徑及初始化參數；42-byte 正常觀測不等於漏洞觸發。 |

來源：CNA 公告、[上游修補](https://github.com/madler/zlib/commit/5c44459c3b28a9bd3283aaceab7c615f8020c531)、[上游 1.2.12 版本](https://github.com/madler/zlib/releases/tag/v1.2.12)、[公開技術說明](https://www.openwall.com/lists/oss-security/2022/03/28/1)。判讀需考慮 default strategy 也可能選用固定碼，不能把沒有明設 Z_FIXED 當成排除依據。

這些是受控單一成品的本機實驗；建置收據未簽章。逐字引用與同 hash 可支持追溯，不能外推到公司出貨成品、可信建置身分或所有 zlib 副本。

本輪開發與重驗合計 **13 筆 AI 紀錄、67 次模型呼叫、2408079 reported tokens**，包含舊版、失敗、接續及上述最終版。不是一次使用的成本，也不是费用金額。前期多次因單檔往返、引用修正及收尾開銷超出門檻；最後一輪有明確程式／提示修正，仍保留全部失敗，不以成功輪取代歷史。gamma 成功鏈是從頭 5 calls 再接續 3 calls，合計 289380 tokens／194.835 秒；不能說成 3 calls 從頭完成。模型步驟不同，單輪比較不證明穩定費用改善。

## 第二項目標的剩餘驗收門檻

1. 固定代表案例與預算，能穩定把已讀材料整理成完整報告；需保留全部失敗，不以不停重試代替通過。本輪 gamma 已接續完成，從頭單輪與重複執行的穩定性仍未達驗收。
2. 增加不同漏洞機制、vendor backport、多副本、材料矛盾／不足／錯配案例，覆核模型建立的必要條件及引用的語意充分性。一次引用合法不代表必要條件定義正確。
3. 以有權提供的公司 ROM＋SDK／SBOM 與同次建置材料做驗收；本輪受控 ELF 不能替代實際 Turnkey 成品。
4. 正式驗證仍只有 CVE-2014-0160、CVE-2022-37434、CVE-2023-38545 三個 profile。規則庫新增的是可覆核調查方法，任意 CVE 的自動 Affected／Not Affected 尚未做到。
