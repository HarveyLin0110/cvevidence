# 大型材料收件與隔離環境差異

## 大型 ROM／SDK 收件

新增「部分材料：大型 ROM／SDK（單檔）」入口與大型單檔補件。一次一檔、最多 256 MiB；原檔與展開內容合計最多 384 MiB、5000 個檔案。一般材料維持每檔 20 MiB／本次 100 MiB；一般多檔補件與大型單檔補件必須擇一。SDK 封存檔只展開為資料，維持連結拒收及不執行內容的規則。

後端接受 binary stream，以最多 1 MiB 分塊寫入私有暫存檔，網頁不再對部分材料呼叫 getvalue()。Streamlit 上傳元件本身仍會保留上傳內容，這不是端到端的低記憶體 HTTP 串流實作；多人部署仍需要容量規劃與限流。

補件會檢查原材料與新增材料合計是否超過 384 MiB／5000 檔；不只檢查單次新增量。原 run 保留。同一組材料重新封裝會得到相同 archive bytes，避免同一請求重試被誤認為不同材料；封裝檔權限為 0600。

## ROM 隔離環境差異

上一輪 GitHub CI `36194556290` 的實讀案例失敗，而本機通過。加入獨立預檢後，`36195303862` 明確回報 `bwrap: loopback: Failed RTM_NEWADDR: Operation not permitted`。

產品改為回報 `ISOLATION_UNAVAILABLE`，網頁指示部署維護者檢查環境，不要求使用者重傳相同 ROM、不降級成非隔離讀取。原 CI 主工作保留，受限制主機驗證明確停止解析；另加 Ubuntu 22.04 的 `firmware-reader` 工作，設定 `CVEVIDENCE_REQUIRE_FIRMWARE_READER=1`，缺工具、隔離不可用或實讀失敗都必須讓工作失敗，不能把停止解析當成功。

`36195577598` 主工作通過；獨立工作進到隔離環境後，因 unsquashfs 4.5 的 `-version` 輸出版本但回傳 1 而停下。預檢改用隔離環境內的 true 命令，後面的嚴格 ROM 實讀測試仍保留。沒有變更主機 AppArmor／sysctl 或減少產品隔離設定。

## 驗收與界線

- 新增八項大型材料測試：真實 24 MiB 分塊輸入、重試封裝及請求冪等、單檔／格式／容量拒絕、解壓共用預算、累積補件限制、SDK 資料展開、原 run 不變、網頁單檔模式。
- 本機新建測試 SquashFS 填充至 24 MiB，經檔案串流建立 run `1f50072f-e95c-447b-85f0-45e2d746cc6d`，原映像大小 25165824 bytes，隔離固定路徑讀取為 PARTIAL_READ。
- 實際瀏覽器確認大型單檔入口、容量說明、未選檔時不可提交；載入上述 run 後看到 ROM 讀取狀態及 curl 8.3.0-vendor2 候選。這不是瀏覽器原生選檔器上傳验收，亦非真實公司韌體或新模型 LIVE。
- 最後版本在 `CVEVIDENCE_REQUIRE_FIRMWARE_READER=1` 下完整回歸：**483 passed、23 subtests passed，285.23 秒**；只有既有 ZIP 重複名稱警告。本機實讀為必要條件，不能以隔離不可用替代。GitHub CI 仍須主工作與獨立實讀工作都通過。
