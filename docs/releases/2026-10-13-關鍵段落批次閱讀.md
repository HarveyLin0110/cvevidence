# 關鍵段落批次閱讀與收尾排程

上輪實測中，delta 的材料已有實作、入口與運作檔，但模型在未讀關鍵迴圈時先交階段報告。本輪處理這個已知缺口，沿用 Sol／high、200000 token 停止門檻與既有唯讀工具範圍。

## 輸入與行為

- `READ_BATCH` 新增 `read_ranges`：一次指定 2–3 段各自的 source ID／起迄行，可來自不同檔案或同檔不同區段。既有共同行範圍仍支援；兩種格式不能混用。每段 200 行／24000 UTF-8 bytes、整批 48000 bytes 的限制不變。
- 批次開始前先驗所有參數。個別容量／格式問題保留其他成功摘錄；來源變動或範圍外 ID 仍使整批失敗。成功閱讀與接續、補件門檻、引用核對共用原機制，不把搜尋定位當已讀完整實作。
- 報告已能以 REPORT 一次提交，排程不再套用舊版兩次收尾：估計剩兩次且條件尚待覆核時，建議一次最重要的定點閱讀，再 REPORT。真正需要使用者材料時仍保留 REVIEW／ASK_USER，不能藉 REPORT 繞過補件檢查。
- 公告 brief 的 references 與 reference_details 網址完全同序相同時，僅在送給模型的封包共用一次，CNA／ADP 出處、全部明細與截短標記保留。保存的公告／歷史不修改，不以 byte 減少聲稱同額 token 或費用節省。
- 新 schema 要求 `read_ranges` 欄位；舊模型收據沒有此欄仍可重用既有格式，原決策不補寫欄位，保持 provider 呼叫歷史一致。

## 驗收標準

1. 不同位置的實作、入口、運作材料可在單輪批次中回傳，各自保留可重驗的 X-ID。
2. 跨 scope、改檔、錯誤／過量範圍不能變成成功閱讀或繞過容量限制。
3. 新 LIVE 從新工程 run 開始，以既有公開／TEST_ONLY 材料測 OpenSSL 舊實作、同版本回補與 curl HSTS 修補；不向模型提供預期答案或指定工具步驟。
4. 除流程是否結束，另查是否真正回傳關鍵段落、引用／條件判讀是否合理、真正缺件是否最小，以及原工程判定是否保留。

固定此階段版本：全量 **868 passed、23 subtests passed（244.77 秒）**，一筆既有重複 ZIP 警告；schema export 與 Git 一致。

curl 的版本／原碼線索沒有被當成成品排除；公告所述的 HSTS 啟用、父子網域與快取前提仍待同成品證據，參見 [官方公告](https://curl.se/docs/CVE-2024-9681.html)。這組無成品、無部署紀錄，不要求先重現漏洞。三筆保存紀錄與原文／位置重新驗證，正式工程結果都保持 NEEDS_INVESTIGATION。

三案有 17 次呼叫，已知回報 tokens 合計 486495；因逾時呼叫用量未知，不能當作完整費用或總用量。此輪改善了可用閱讀能力及 curl 的跨段查核，尚未證明 OpenSSL 穩定完成；下一步處理重抄公告 diff 造成的格式修正。原始收據留於 Git 忽略的 `var/validation/targeted-reading-20261013/`。公司材料、金鑰、成品及 API 回覆不提交。

## 邊界與協作

批次回傳原文不等於模型充分理解，更不等於可信建置或正式 CVE 判定。任意 CVE 的深度／穩定性仍須跨案例驗收，不用兩三個案例宣告完整達標。
