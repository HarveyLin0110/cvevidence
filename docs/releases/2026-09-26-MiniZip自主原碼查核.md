# MiniZip 自主原碼查核與修補證據範圍

本輪以 CVE-2023-45853 檢查「不指定工具步驟，AI 能否找出相關函式與修補檢查」。發現 CNA 提供 GitHub PR 843，而原政策只支援 commit，漏掉修補 patch；另外首次模型收尾誤把「修補副本未編入」當成可以停止查核的理由。

## 修改

- CNA／ADP 中符合固定格式的 GitHub PR 連結，轉成 GitHub patch-diff 主機的固定 patch 路徑；不跟隨 redirect、不接受任意模型 URL，沿用公開 IP、大小與共用期限限制。
- 保存原始參考 URL、實際 patch URL、出處及 bytes hash。PR 與等效 patch URL 去重時保留第一筆參考與順序。PR patch 可變，保存 hash 只代表本次內容，不保證 PR 已合併或可信建置來源。
- PC 提示明確區分：修補副本未編入只能否定該份修補證據的適用性，還要查實際副本及 bundled/static 副本；材料中沒有成品，也不能推論產品不存在。這是模型指引，並非完整的自動語意驗證器。

## 材料與驗收

新建 TEST_ONLY 套件清單聲明 zlib 1.3-vendor1；zip.c 是上游 v1.3.1 固定提交 51b7f2abdade71cd9bb0e7a373ef2610ec6f9daf 的原文，保留授權標頭，SHA256 為 213f853d71266ebe8d8335740cfe94b0731009d8fb3f7e6ae01a627398732ec8。材料說明明示只是模擬 vendor 回補比對，沒有真實公司成品或建置關聯；不執行原碼或漏洞，也未複用舊 Demo。

兩次實際 Sol／high 使用相同材料與使用者問題，未指定 SEARCH／READ 等步驟。工具取得 CNA、Debian、Gentoo 與 PR patch；模型自行搜尋 zipOpenNewFileInZip4_64 並閱讀產品原碼。

- 初次 ed8bb7cc-7c39-4bff-b13a-acb11bb30c24：6 calls、98.02 秒、122792 tokens，步驟成功，但收尾存在上述不妥的停止推論；不作全面成功案例。
- 加強提示後 ea19b367-2531-4b04-bff3-5b5997f9c041，工程 15027e68-57b0-42a5-a4fb-e0a5c51de3e1：7 calls、122.08 秒、151797 tokens。指出 zip.c 的 filename、comment、local/global extra field 四項 0xffff 防護及後續配置／複製位置，條件直接引用取得的修補 patch。
- 第二次仍明示成品身分、source→object/archive→成品與其他副本未知。一次 COMPLETE 因未按既有規則提出結構化補件被拒絕，隨後 ASK_USER 完成，只要求一份同 build 既有 link map 或等效 manifest，未索取整套 SDK 或 PC3 動態測試。

這證明此案例能自行定位實作、比較修補並留下最小缺口；不能外推所有新 CVE、證明公司產品安全或把提示當形式保證。模型用量與等待時間仍高，後續需跨案例量測。

來源聚焦測試 27 passed，涵蓋 PR 映射／出處、URL 限制、去重與第一筆順序。首次完整回歸 633 passed、23 subtests passed（266.38 秒）；加入順序測試與提示後最終 634 passed、23 subtests passed（272.89 秒），既有重複 ZIP 名稱警告一项。來源 4aad581、提示 b0abb72 分開提交。
