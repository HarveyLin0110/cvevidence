## 趕時間是否留下了強制快速查找

有舊 focused 模式及其 2–4 次優先目標，主要供相容入口；目前網頁 worker 明確使用 `analysis_depth="pc"`，附加 PC 深度指令覆盖该速度目標。正常 profile 核心 145 秒／UI 180 秒，通用核心 240 秒／UI 300 秒，最多 12 次呼叫。這些是目前資源邊界，不是仍在沿用比賽提交截止。

因此現況的主要限制不能只靠加時間處理。材料辨識、修補語意、同成品綁定、PC3 觀測和覆核閉環各自要補功能或證據；加大預算可能只是花更多時間重查。保留停止／接續，量測關鍵位置命中、重複補件、錯誤排除及人工可用性，比取消所有上限更符合既有設計。

## 本次直接修正

1. **用量未知被算成完整**：空 usage、缺少欄位、無效值原本也計入已完整回報，nullable total 也未正確回退至 input＋output。改為只計非負整數，缺值顯示不完整；保留已知下界，cached input 不重複加總。原始 provider receipt 不改寫；兩來源共用同一停止門檻。
2. **checkpoint 損壞遮蔽終止結果**：在 timeout／cancel 處理中讀到壞 JSON 會直接拋出，沒有 end receipt。現在仍保存 TIMED_OUT／CANCELLED，標 `AI_CHECKPOINT_REJECTED`，不附損壞內容、不重送；原工程 bytes 不變。網頁讀壞進度也改成可見錯誤而非 traceback。
3. **個人分支 push 沒有 CI**：現有 workflow 只對 main、舊 Frankie 分支及 PR 觸發。增加 `codex/horace-development` 的 push 測試，保留全部 pytest、schema 差異檢查及合併權限。

這些修正不擴張 CLI 工具，不更換模型、不增加 API 外送或取消預算，不讓 AI／人工自由文字直接改 assessment。

## 建議接續順序與驗收門檻

1. **先完成網頁人工覆核閉環**：逐條給 supported／excluded／unresolved／conflict 與理由，綁定精確 dossier 和 AI ID，保存獨立收據並加入報告。驗收跨 run／資料改動拒絕、舊結果不變、未認證身分明示。仍不把勾選等同正式安全判定。
2. **改善一般產品的最小資料辨識**：先選一類實際客戶可提供的 SBOM／套件清單／build record，定義解析能力及缺口，再擴充格式。驗收名稱別名、未知版本、回補版與不足資料；不能將未識別解讀為零漏洞。
3. **為新 CVE 建立真正可審查規則**：每次選一個，定義必要／排除條件、跨版本原碼與成品綁定、正反例和範圍外拒絕，再准許正式判定。不要讓模型即時產生的 PLAN 自動成為正式規則。
4. **補同版本雙來源與多案例品質驗收**：完整／缺件／提前补件／新入口／回補／範圍外各案例，以同資料比較 API／CLI，記成本用量、重複查詢、正確補件與錯誤 Not Affected；人工判讀引用支持關係。舊成功紀錄不能代替此 gate。
5. **完整瀏覽器上傳、補件與下載验收**：使用使用者實際操作的檔案選擇器走 SBOM→原碼補件→報告下載，核對下載 bytes、中文檔名、衝突／超限及刷新。現有受控路徑與 AppTest 不算這項完成。
6. **最後再擴成多人服務**：依實際部署需求補使用者身分、案件權限、背景任務持久化與維運；本機 API／Codex 帳號不要默認轉成公共共用帳號。

以上是仍未完成的開發項目，未列為本次已交付；本輪直接交付範圍是前述三項可靠性／CI 修正與這份可追查審核。
