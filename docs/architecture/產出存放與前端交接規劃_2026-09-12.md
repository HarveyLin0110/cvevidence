## 4 真實工程包與版本怎麼放

資料使用明確版本，例如 `demo-3x3-2026-09-12-r1`。這是命名示例，尚未表示資料已建置。

```text
var/artifacts/datasets/<dataset_version>/
├── packages/
│   ├── 01_firmware/
│   ├── 02_firmware/
│   ├── 03_firmware/
│   ├── 04_cmake/
│   ├── 05_cmake/
│   ├── 06_cmake/
│   ├── 07_curl/
│   ├── 08_curl/
│   └── 09_curl/
└── supplements/
    ├── 03_firmware/
    ├── 06_cmake/
    └── 09_curl/
```

今天新寫的工具統一輸出小寫 `packages/`，catalog 記 `package_root: "packages"`。附件中的 `Packages/` 是舊資料格式，不能把新舊路徑或 archive hash 混用。

| 部分交付 | 補件原檔從哪裡取得 | 同版核對 |
| --- | --- | --- |
| `03_firmware` | 今天 `02_firmware` 的原始建置材料 | 同一個 ROM／產品成品 hash |
| `06_cmake` | 今天 `04_cmake` 的原始產品與建置材料 | 同一個更新工具成品 hash |
| `09_curl` | 今天 `07_curl` 的原始啟動、設定與使用材料 | 同一個 curl 與受評估產品身份 |

每個部分包有自己的 manifest，如實列出實際交付內容。補件有獨立材料身份及 manifest；合併分析時建立新輸入快照，不能覆寫原包。manifest 保存一般檔案雜湊與 symlink 類型／目標，解包時核對連結範圍。

先交完成的 ROM 一列，讓 Frankie 串接；不等九包齊全才交件。已發布 catalog 保持不變，後續新增 CMake 或 curl 時發布下一個 dataset 版本，引用已存在的固定 artifact 即可，不必重複上傳相同包。

建議按 ROM、CMake、curl 分別封裝，vendor bundle 另包。每個 archive 有自己的名稱、byte size 和 SHA-256；完整九格 catalog 組合這些 artifact。重新封裝或修正資料就取得新 hash 和版本，保留舊版本供歷史 run 重現。

### catalog 需要記什麼

至少包含 `schema_version`、`dataset_version`、artifact ID／檔名／大小／hash、穩定的儲存參照、包根目錄、每包相對路徑與 manifest hash、build 身份、補件關係，以及相容的 contract、collector、profile 和 builder 版本。

以下只是結構草稿；正式可匯入 catalog 的必填值必須實測填齊，`DRAFT` 及 `null` 不可當成已驗資料：

    }
  ],
  "packages": [
    {
      "package_id": "03_firmware",
      "artifact_id": "rom-row-r1",
      "relative_path": "packages/03_firmware",
      "manifest_sha256": null,
      "build_id": null,

      "supplement_id": "03_firmware-supplement",

## 5 一次分析產生的結果怎麼存

採用附件的識別關係，**統一使用 `analysis_request_id`**，不再另外使用 `request_id` 表示同一件事：

```text
product_id → release_id → analysis_request_id
                           ├── cve_id A → run_id
                           └── cve_id B → run_id
```

現象入口尚未知道產品、版本或 CVE 時先建立草稿 case，相關欄位可為空。取得足夠資訊才建立 CVE 查核 run，不能為了存放路徑先編造產品或 CVE。

### 每個 run 的建議檔案

```text
var/runtime/runs/<run_id>/
├── run.json                      身份、模式、狀態、版本、parent_run_id
├── input-snapshot.json           當次原始資料與補件的固定引用
├── queries/
│   ├── Q1_COMPONENT.json
│   ├── Q2_BUILD.json
│   ├── Q3_IMPLEMENTATION.json
│   ├── Q4_BINDING.json
│   └── Q5_PATH.json
├── evidence.json                 已驗事實、原始值、位置與來源
├── conditions.json               各 CVE 必要條件與缺口
├── assessment.json               成功產生的工程判定；未產生則為 null
├── ai/
│   ├── investigation-tasks.json  AI 新提出的 query 及補件工作
│   ├── tool-events.jsonl         真正執行的工具、來源與結果
│   └── advice.json               引用、說明、未解處及下一步
└── events.jsonl                  階段、時間、失敗與完成紀錄
```

這是後端建議的序列化形式，不要求 Frankie 的前端知道這些檔名。SQLite 可保存產品、release、case、request、run 索引與覆核狀態；大段結果與原檔保存在檔案區。若現有後端已用 JSON，保留現有方式並提供同一 API，不另維護第二份完整結果。

run 執行中可追加事件；完成後固定其輸入與結果。後端先完成結果檔的原子寫入，再發布完成狀態；避免前端讀到寫一半的 JSON。報告和重播只引用已完成快照。

### AI 新增 query 的紀錄

每項保存 `task_id`、`question`、簡短 `reason`、`trigger_refs`、目標範圍、`action`、`source_ids`、`status`、`result_refs` 和 `unresolved`。實際呼叫另記工具名稱、參數、結果引用與耗時，不把整包工程檔重複塞進每筆事件。

`ASK_USER` 工作要能連回補件回覆；收到新材料後產生新 run，使用 `parent_run_id` 指回原 run，保留原查詢與問題。新增工作的內容由當次資料決定，不能只把固定 Q6 或預寫答案存成「AI 已調查」。

### Evidence 要能找到同一份原始 bytes

Evidence 至少帶 `artifact_id`、manifest／檔案 hash、相對路徑、行號或其他精確位置、原值、fact 類型與成品範圍。後端按 run 的輸入快照解析引用；`E-001` 之類短 ID 只能在該 run 內查找，不能跨產品全域搜尋。

原檔不按 CVE 或 run 重複複製。同一 artifact 可被多個 run 引用；每個 run 都保存自己的引用集合及 context hash。額外文字保存為使用者材料，和可支持正式判定的已驗事實分開。

## 6 Frankie 要如何接我們的結果

### 我們交四樣東西

1. **程式版本**：包含 builder、collector／Verifier、CVE profile 與必要依賴設定的 commit；未提交前明確標尚無 commit。
2. **契約版本**：AnalysisRequest、Run、QueryResult、Evidence、Condition、Assessment、Supplement、Advice，另加 InvestigationTask 和 ToolEvent。
3. **資料版本**：catalog、固定工程 archive 與供應商補充材料；不把本機 `/home/...` 路徑當整合契約。
4. **驗收摘要**：實際通過／失敗、操作方式、已知缺口、完整驗收報表的位置與 hash。

Frankie 先拉程式與契約，再取得所選 artifact、核對 archive 及 manifest，註冊成可用 package。使用者選包後，Runner 只開放該包與此次已提交補件的來源，不能把整個 dataset、factory、tests 或 validation 目錄交給模型。

### 前端只接 API

下表是介面職責草案，正式路由名稱由 Frankie 在 `contracts/` 統一；不是宣稱已有 endpoint：

| 介面職責 | 回傳或接收的內容 |
| --- | --- |
| 列出可用資料 | dataset／package ID、顯示名稱、可用狀態；不含預期答案 |
| 收件與候選發現 | 現象、使用者回答、檔案需求、候選 CVE 及公告依據 |
| 建立分析 | analysis_request_id、各 CVE 的 run ID 與等待狀態 |
| 讀取 run／事件 | 工程與 AI 狀態、Q1–Q5、條件、結果、追加 query 與補件工作 |
| 展開證據 | 在該 run 範圍內解析 Evidence，回傳原文、位置及 hash |
| 提交補件 | 文字／upload ID、適用範圍；回傳新 run 與 parent_run_id |
| 下載交接報告 | 固定 run 的報告，不由前端臨時拼成另一份判定 |

前端不得以等待秒數、package ID 或示例 A／B／C mapping 決定 verdict。合成範例放 `contracts/examples/` 或獨立 demo mode，不混入正式 Runner。基礎 Query 完成與漏洞是否受影響是不同狀態；PC 分組由 profile 回傳，不在前端寫死 Q4 一定等於 PC3。

最新前端若仍是七個互相依賴的 HTML／JS／CSS，先整組納入 `apps/web/` 並保持載入順序；路徑搬移與前端模組重寫分開。現有應用只有一套共用核心，抽取到 `src/cvevidence/` 後由原入口 import，不複製兩套維護。

## 7 報告與交接檔怎麼分

| 產出 | 保存方式 | 使用者／用途 |
| --- | --- | --- |
| builder 驗證產物、位址與正常觀測 | 完整檔放 `var/validation/<validation_id>/` | Horace 查建置與證據；不是正式產品 verdict |
| Runner 的 Query／AI／工程判定 | 放 `var/runtime/runs/<run_id>/` | 網頁、歷程、補件重查 |
| 使用者下載的報告 | 放 `var/exports/reports/<run_id>/` | 工程交接；附範圍、來源、未解事項與覆核狀態 |

`handoff.json` 記 code commit、dataset 版本、catalog hash、archive 清單與 hash、contract／collector／profile 版本、驗收摘要及所需啟動設定鍵名。實際秘密值不放入交接檔。這份索引供部署與驗收，不能作為某次 run 的證據輸入。

今日 builder 應明確接收 output root，把生成資料寫進 `var/`。`tools/demo-data/` 只放程式、來源 pins 和必要 patch，避免生成到原碼目錄後才補大量忽略規則。

不用全域 `*.json`、`*.log`、`*.zip` 或 `build/` 忽略規則，以免隱藏 schema、必要 fixture 或建置程式。`.gitignore` 不會移除已追蹤的檔案；整合時仍需核對實際 Git 提交清單。[Git 官方 gitignore 說明](https://git-scm.com/docs/gitignore)

文字原碼可用 `.gitattributes` 約定換行；封存工程包保持原始 bytes，不進行換行正規化或展平 symlink。一般 Git 對超過 100 MiB 的單檔有限制，因此完整工程包使用 artifact 發布，不提交整包 ZIP 或解壓後的中間產物。[GitHub 大檔案說明](https://docs.github.com/en/repositories/working-with-files/managing-large-files/about-large-files-on-github)
