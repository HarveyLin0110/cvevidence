# 核心分析介面與接線提案

提供者 Horace；消費者 Frankie 的共用 Runner。此文件記錄已實作的核心入口與欄位；映射到 Frankie contracts 的方式仍待整合確認。Horace 不新增另一套正式 Runner、Web 或保存系統。

分工依最新「工具架構與雙人分工確認」及同步紀錄：Horace 已承接規則、模型呼叫與 AI 工具迴圈；Frankie 負責正式 Runner、模式入口、保存與整合。Plan V5 較早將規則聚合與 AI adapter 列給 Frankie 的段落，不表示需要再開發第二套核心。

## 最快接上完整分析

```python
from cvevidence_core.frankie_adapter import analyze_archive_for_runner

result = analyze_archive_for_runner(
    "demo-inputs/rom/03_rom.tar.gz",
    {"requested_cves": ["CVE-2014-0160"],
     "symptom": "掃描只看版本認為有 Heartbleed，同事口述已關閉 heartbeat。",
     "mode": "OFFLINE"},
    expected_archive_sha256=catalog_entry["archive"]["sha256"],
    temporary_root=runner_temporary_directory,
    event_callback=emit_event,
)
```

切成 `LIVE` 時，模型使用環境的 `OPENAI_API_KEY`、`OPENAI_MODEL=gpt-5.6-sol`、`OPENAI_REASONING_EFFORT=medium`。本機開發可明確傳 `env_file=".env.local"`；路徑只能來自可信任的 Runner 設定，不能接受上傳檔案或 AI 指定。環境變數優先於檔案。

Frankie 的 M5a 收件 worker 目前刻意不轉交金鑰，這點保持有意義：接 AI 階段時，請由可信任的 AI 呼叫程序取得這三個設定；不要因收件成功便把 AI 顯示為 Live 成功。

網頁建議先以 `mode="OFFLINE"` 完成並保存工程結果，立即顯示第一筆真實判定；再呼叫 `workflow.investigate_after_engineering(context, saved_result, user_context, env_file=...)`。此入口先重核 context／collection，回傳獨立 AI 結果，不改動已保存的工程 dict。Runner 可以在 AI 逾時時保留工程畫面；多 CVE 時也應逐項安排 AI deadline，避免整次逾時吞掉所有工程結果。

壓縮包上限 512 MiB；驗證 archive hash → 解到新的暫存資料夾 → 驗證 manifest/context → Q1–Q5 → 重取證 Verifier → assess → AI。暫存離開函式即清除，結果是可 JSON 化的 dict。正式保存、run ID、parent run、整次 deadline 由 Runner 管。

`expected_context_hash` 可防止分析時引用其他 snapshot。亦可在 Frankie 現有 worker 解包後直接呼叫：

```python
from cvevidence_core.workflow import analyze_package
result = analyze_package(context, requested_cves=["CVE-2014-0160"], mode="OFFLINE")
```

其中 context 是已匯入的 `InputPackage`。無檔案的現象入口可用 `analyze_package(None, symptom="更新匯入失敗")`，回 `AWAITING_INPUT`、候選探索與補資料問題，不捏造 CVE。

## 回傳欄位與畫面對應

| 核心欄位 | 意義與建議畫面 |
|---|---|
| `input.sources` | S-ID 檔案清單；只有 bytes/hash 身分，不是工程事實 |
| `discovery` | 元件與官方資料支持的候選、未知 CVE、現象尚未歸因 |
| `analyses[]` | 每個 CVE 獨立結果，最多指定 5 個；不要合成一個整體安全燈號 |
| `queries[]` | 固定 Q1–Q5；COMPLETED／COMPLETED_WITH_GAPS／CONFLICT |
| `evidence[]` | E-ID、原值、來源 witnesses、X-ID 原文、判讀理由 |
| `assessment.conditions[]` | SUPPORTED／BLOCKED／UNKNOWN、引用的 E-ID |
| `assessment.verdict` | AFFECTED／NOT_AFFECTED／NEEDS_INVESTIGATION |
| `assessment.conflicts` | 交付紀錄互相矛盾；優先要求覆核 |
| `assessment.statement_reviews` | M-ID 使用者文字聲明，仍待原始證據確認 |
| `assessment.gaps/next_steps` | 缺什麼、為什麼需要、同 build 要求 |
| `ai.tasks[]` | AI 新提出的問題、目的、工具動作、結果與補件要求 |
| `ai.excerpts` | AI 查到且精確核對過的原文；不是經證明的語意推論 |
| `ai.calls` | 真實 response ID、模型、API 狀態、token usage；無 API key |
| `summary` | 可供報告組裝的中文標題、結論、缺口、下一步、範圍 |

Q1 元件、Q2 build、Q3 受影響實作、Q4 source/object/library/product 綁定與成品範圍、Q5 輸入路徑與 CVE 必要使用條件。UNKNOWN 條件所附的規則解釋不能顯示成已成立的事實。

工程已完成時，AI 可以是 OFFLINE、NEEDS_USER_INPUT、COMPLETED、TIMED_OUT、API_ERROR、INCOMPLETE、INVALID_CITATION 或 BUDGET_EXHAUSTED。請呈現各自狀態；AI 失敗不表示工程已驗證結果消失，也不能以先前文字冒充本輪 Live。

## 各階段直接呼叫

```python
from cvevidence_core.queries import collect_evidence
from cvevidence_core.verifier import verify
from cvevidence_core.assessment import assess, check_claim, summarize
from cvevidence_core.ai import investigate, replay_investigation

collection = collect_evidence(context, cve_id)
verified = verify(context, collection)
assessment = assess(context, verified, statements=[])
ai = investigate(context, verified, assessment, user_context, mode="LIVE")
```

Verifier 會重新取證，拒絕改過的 fact、ID、原文、hash 或 context。`VerifiedEvidence` 含程序內簽記；跨程序請保存 collection，然後在使用它的程序重新 verify，不要自行建構或反序列化一張「已驗證」證書。

`check_claim(context, assessment, claim)` 的 claim 可包含 `cve_id`、`build_id`、`artifact_sha256`、`verdict`。不同或未指定 build 的舊聲明不得沿用。`interpret_statement(text, context_hash)` 只建立 M-ID；傳入新聲明後採保守覆核，不以文字直接更改條件為 BLOCKED。

## AI 新證據回到判定的流程

`investigation_evidence.reassess_after_investigation(context, assessment, ai_result, statements=...)` 逐條重讀 AI READ／SEARCH 找到的原文，以 source/hash/行號/原值建立新的 E-ID 來源觀測，再執行 collect → verify → assess。workflow 已在成功／等待補件的 AI 階段後回傳 `investigation_verification`；其中保留動態問題、新 E-ID、重判與 verdict 是否改變。

新觀測的 `condition_inference_verified=false`：它證明那些 bytes 存在，不代表 AI 自由推論已成立。只有已審查 profile 的確定性提取能把內容轉成正式條件；超出 profile 的推論仍需補件或工程覆核。在同一 snapshot 只多查幾個原文，正式結果可能不變。真正收到同 build 新檔案時，仍走新 snapshot 的完整重取證，不把上一個 context 的 AI 原文搬進來。

## 補件、歷史與事件

沿用 M5a 的 delta 合併：validate_supplement → 建新 snapshot/archive → 重跑完整分析 → 保存 parent run。原始 archive、context、結果不覆寫；不同 build 改走另一個成品案件。

event_callback 收到 `stage/status/cve_id`，階段依序為 INGEST、QUERIES、VERIFY、ASSESS、AI。請自行加入 Runner run ID、時間與畫面進度；不要把 AI 簡短調查理由標成模型內部思考過程。

Replay 只接受同 context、hash 一致且原文仍可核對的既有 Live 紀錄，顯示 `mode=REPLAY`。它是可核對的舊紀錄播放，不能宣稱本次模型呼叫成功；本機 hash 也不構成第三方簽章認證。

## 已知範圍

目前深度規則只支援今日三種格式與已審查 source 版本。未知 CVE 保留 `UNSUPPORTED_CVE`、assessment=null；已知 CVE 但不支援的交付格式回 Needs Investigation。匯入完整性失敗則應由 Runner 保存失敗狀態與 assessment=null。

分析器不執行上傳 binary；ROM 用可信任的系統 `unsquashfs` 解析、ELF 用 `readelf`。在 Linux 主機須安裝 `squashfs-tools`、`binutils`。函式層的工具預算不取代 Runner 的整次程序 deadline。

## PC 分組與 Replay 時間（本輪補齊的呈現欄位）

每個已支援的 `analyses[]` 新增 `condition_groups`，這是呈現語意，不進 assessment hash、不改 Evidence ID，也不改正式規則。舊工程 JSON 仍可供 `investigate_after_engineering` 重核；缺分組的舊檔可用 `assessment.describe_condition_groups(cve_id)` 取得已審查 profile 的分類。未知 CVE 不借用其他 profile 的分組。

| 顯示區 | 對應 condition_id |
|---|---|
| 共用前提 | build_identity、library_binding、product_binding、scope_complete |
| PC1 元件適用性 | component |
| PC2 實作與修補 | vulnerable_implementation |
| PC3 產品輸入路徑 | entry_reachable、trigger_prerequisites |

共用前提必須與各組一起看；不要把每組再折成一個布林判定。每個條件原本的 SUPPORTED／BLOCKED／UNKNOWN、evidence_ids、說明均保留。前端接入為新增選用欄位，Runner 仍保存核心原 JSON。

新 Live 紀錄有 UTC ISO 8601 的 `started_at`／`finished_at`。`replay_investigation` 返回 `original_started_at`、`original_finished_at`、`original_time_available`、`replayed_at`、`original_record_hash`；本次不呼叫模型。舊紀錄若沒有原時間，顯示「原執行時間未記錄」，不能以播放時間代替。來源 context／原文／record hash 核對仍保留。

AI 每次 request 的 `calls[].runtime_budget` 記錄含本次的剩餘呼叫數與剩餘秒數；修正引用仍消耗同一預算。最後一次未完成時仍顯示 BUDGET_EXHAUSTED，不能把提示要求收尾誤當成功保證。
