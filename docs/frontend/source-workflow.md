# 產品資料自動匯入與查核流程

## 導覽設計

1. 產品與資料來源：產品＋版本查找、指定資料路徑、手動補充。情境／CVE 為選填，無 CVE 時先做元件識別再由後端提出待確認的 CVE 範圍。
2. 資料確認與缺件：呈現來源位置、候選材料、同次建置核對、需要補什麼。候選與驗證成功分開，不因檔案存在就宣稱證據成立。
3. 分析進度與結果：五個 Query、三個 PC、证據引用、未知條件、錯誤／重試。
4. 報告與後續行動：初判、限制、缺件、覆核，以及返回補件建立新 run 的入口。

AI 建議、證據瀏覽、補件與版本歷程是可重複進入的工具，不是只能前進一次的步驟。沒有結果時報告停用；有部分結果時可產出含未知項的階段報告。資料不足不阻止所有查核，但不得將未知轉成不受影響。

## 自動取得資料的正式契約（待實作）

產品索引：product_id + release_id → build_id → material manifests。版本匹配多個 build 時讓使用者選擇，不默默選最新。資料位置應指向已配置的 connector 與受允許根目錄，不讓公開 API 對任意使用者輸入路徑進行讀取。

路徑查找：由部署於工程環境的代理或後端 connector 讀取授權位置。瀏覽器輸入 Windows／WSL／NAS 路徑只是描述來源，不表示雲端服務具備存取權；權限不足、位置不存在、零匹配、版本衝突需各自顯示。

候選匯入：列舉與分類 → 檔案大小／格式限制 → hash 與 provenance → build 關聯核對 → 使用者確認材料集合 → 不可變 input snapshot → 執行 Query。不要直接執行資料包內的腳本，不把檔名或供應商說明視為驗證成功。

材料紀錄應包含 material_id、source_id、relative_path、kind、size、sha256、product_id、release_id、build_id、discovered_at、validation_status。來源的任意文字視為資料，不作為 AI 指令。

缺口紀錄包含 gap_id、query_id、pc_id、reason、requested_material、priority、status、evidence_refs。AI 問題連結 gap，而非自行更改 PC 或終局判定。補充說明與可驗證的原始證據分別儲存。

報告後補件：保留原 run 與報告 → 匯入新材料 → 驗證相同產品／build → 新 run 帶 parent_run_id → 重跑受影響 Query 與下游規則 → 比較新增證據、解除與剩餘未知。跨 build 的資料應另開查核，不混入舊結論。

## 本次交付邊界與驗證

已實作 sources.js 前端互動與四步導覽。資料來源只存頁面記憶體；沒有實際掃描、上傳、產品資料庫查詢或 AI 呼叫。候選清單為固定樣例，沒有套用實際產品分析結論；繼續模擬結果仍建立獨立示例產品。

已於公開預覽驗證：空路徑錯誤、路徑進入資料確認、缺件清單、AI 建議到獨立模擬結果、報告回到補件入口、切回原產品仍保留路徑、第一頁桌面視覺。真正 connector、權限、持久化、手機實機尚未驗證。
